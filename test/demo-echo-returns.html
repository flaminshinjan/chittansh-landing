Echo Returns

An inbound voice agent that contains 38% of returns & exchange calls end-to-end on a DTC apparel store. Sub-1.4s latency, real OMS tool-use, clean escalation when policy gets ambiguous.

The problem we were handed

The customer ops lead at a DTC apparel brand walked us through the queue numbers on call one. 4,000 inbound calls a month, 71% of them about returns, exchanges, or order status. The BPO they used charged per-minute and hit a service-level cliff every time a campaign launched.

They’d tried two voice vendors before us. Both demoed beautifully and neither shipped. The first one couldn’t hit a latency budget. The second one couldn’t hold an OMS handle for a full call.

The decision we made on call two

The biggest architectural call was on streaming. We refused to put a turn-based stack into voice. Every vendor that does turn-based voice agents (record → ASR → reason → TTS → play) eats 2.5–3.5 seconds per turn. That’s a dead conversation.

So we built on a streaming reasoner with partial-token TTS, sub-1.4s end-to-end median. The agent starts speaking before it’s done thinking. Sounds like a human pausing, not a robot waiting.

What tool-use looks like in production

The agent has direct, audited access to the OMS, the WMS, the payment processor and the carrier API. Each tool call is wrapped, logged, and reversible. The escalation policy is explicit: anything outside the policy window goes to a human with full transcript and context.

We don’t let the agent improvise on refunds. The policy lives in code, not in a system prompt.

The third call was a status review. We were already live on 5% of inbound traffic by then.

What changed for the business

The 38% containment number is the headline, but it's not the one ops cared about most. They cared about first-call resolution on the 62% that escalate. Because the agent hands the human a transcript, a customer profile and a proposed next action — FCR on escalated calls went up 31%.

The other thing that mattered: the agent generates a weekly insights pack from anonymised transcripts. Top exception reasons, fulfilment time complaints, copy issues — straight to product and ops. The voice queue became a research instrument.

The architecture, briefly

  • Telephony. SIP ingress into a streaming reasoner. Twilio + Plivo failover.
  • Reasoning. Claude with explicit tool schema, streaming output, partial-token TTS.
  • Tools. Direct, wrapped API access into OMS, WMS, payments, carrier. Reversible.
  • Audit. Every action recorded with rationale + state diff. Replayable for review.
  • Escalation. Policy in code. Out-of-policy → warm transfer with full context.

What broke

The first week, we underestimated how often callers swap context mid-call. ("Actually, can I exchange instead of return?") The agent would commit to one tool path and stall. We rebuilt the dialogue policy to keep multiple tool intents alive until the customer confirms. Latency went up by 80ms. Worth it.

The second thing that broke: a regional carrier API returned status codes outside the spec. The agent saw "unknown" and escalated every time. We added a fallback path that retries with a different carrier integration. Most ops teams never see this kind of stuff — it’s where the value lives.
